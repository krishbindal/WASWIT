# Viva Questions and Answers

## Project
1. **What is WASWIT?**
   WASWIT (Workload-Aware Intelligent Selection between JavaScript and WebAssembly) is a deterministic runtime selection toolkit that empirically routes workloads to either JS or WASM.
2. **Why JavaScript vs WebAssembly?**
   While WASM is generally assumed faster, overhead from the JS-WASM boundary and memory allocation means JS can be faster for small input sizes or specific workloads.
3. **What problem are you solving?**
   Developers lack a deterministic framework to automatically decide when to use JS versus WASM without writing manual, overhead-heavy dynamic profilers.
4. **Why is runtime selection necessary?**
   Because no single runtime is universally faster across all possible workloads and input sizes.
5. **Why not always use WebAssembly?**
   WASM incurs instantiation, serialization, and boundary-crossing overhead that can easily dwarf the execution time of small payloads.
6. **Why not always use JavaScript?**
   JS suffers from JIT warmup delays, garbage collection pauses, and slower mathematical processing on large, computationally heavy workloads compared to compiled WASM.

## Research
7. **What is the research gap?**
   The lack of rigorous, empirical crossover thresholds mapping specific mathematical/computational workload sizes to the most efficient browser runtime.
8. **What are your research questions?**
   Does adaptive runtime selection, governed by an empirical policy, prevent statistically significant performance degradation compared to single-runtime hardcoding?
9. **Why use independent evaluation?**
   To ensure the policy generated during the calibration phase does not overfit to the exact samples used, thereby validating it against unseen inputs.
10. **Why use multiple workloads?**
    To prove that crossover thresholds vary fundamentally depending on the nature of the computation (e.g. integer sorting vs cryptographic hashing).
11. **Why use calibration?**
    Calibration provides the empirical data required to generate deterministic crossover thresholds.
12. **Why freeze the policy?**
    A frozen policy guarantees deterministic behavior for developers and provides an immutable basis for scientific evaluation.
13. **Why separate calibration and evaluation?**
    To avoid data leakage, ensuring the statistical evaluation represents true out-of-sample performance.
14. **Why use 10 replicates?**
    To provide a sufficient sample size (2^10 = 1,024 permutations) for the exact paired sign-permutation test to detect significance at an alpha of 0.05.
15. **Why 30 measured iterations?**
    To stabilize the micro-benchmark measurements and absorb transient OS jitter.
16. **Why 5 warmups?**
    To ensure the JS JIT compiler has optimized the execution path, simulating steady-state performance rather than cold-start anomalies.
17. **Why sign-permutation testing?**
    Browser execution timings are notoriously non-normal, heavily skewed, and heteroscedastic. Non-parametric permutation testing makes no distributional assumptions.
18. **Why Holm-Bonferroni?**
    To control the family-wise error rate across 39 simultaneous statistical tests, preventing false positives (Type I errors).
19. **What does 0/39 significant tests mean?**
    The specified analysis did not establish statistically significant differences under the multiplicity-adjusted testing procedure, indicating the adaptive policy did not cause statistically significant performance regressions under worst-case comparisons.
20. **What are the threats to validity?**
    Environment specificity (only evaluated on Blink/Chromium 138), restricted workload set, and reliance on simulated inputs.

## Technical
21. **How does the selector work?**
    It takes workload characteristics, looks up the frozen policy rules, and deterministically returns "javascript" or "wasm".
22. **How is input size derived?**
    Deterministically based on the length of the typed arrays passed (e.g. `n` for matrix, `array.length` for sorting/hashing).
23. **How does the WASM module load?**
    Via native ESM `import.meta.url` pointing to the pre-compiled `.wasm` binary generated by `wasm-pack`.
24. **Why measure selection overhead separately?**
    To prove that the deterministic lookup table overhead is negligible (typically < 0.1ms) and does not cancel out the performance gains of intelligent selection.
25. **How does the SDK work?**
    It abstracts validation, analysis, and selection behind a single asynchronous `waswitRun()` interface.
26. **Why use TypeScript?**
    For strict type safety, self-documenting APIs, and preventing incorrect array types from reaching the WASM boundary.
27. **How does the developer package work?**
    It bundles the SDK using `tsup` into CJS and ESM formats, distributing the raw WASM alongside the JavaScript.
28. **How does a developer integrate WASWIT?**
    By installing the tarball/package and calling `waswitRun({ workload, input })`.
29. **Does the SDK dynamically benchmark JS and WASM?**
    No. It relies entirely on the frozen empirical policy to eliminate real-time benchmarking overhead.
30. **Does WASWIT use AI?**
    No. It is purely deterministic and empirical.

## Limitations
31. **What browsers were evaluated?**
    Chromium/Blink (v138) on Windows.
32. **Why is the policy environment-specific?**
    Because different JavaScript engines (V8 vs SpiderMonkey) and architectures have vastly different JIT profiles and WASM compilation speeds.
33. **Why isn't WASWIT universally optimal?**
    A crossover point found on a high-end desktop running Chrome will differ from a low-end mobile device running Safari.
34. **Why is Node.js CommonJS currently limited?**
    `wasm-pack` with `--target web` relies on ESM-specific `import.meta.url` features that crash in strict CommonJS contexts without bundlers.
35. **What workloads are currently supported?**
    Matrix Multiplication (Float32), Merge Sort (Int32), and SHA-256 (Uint8).
36. **What would you improve in future work?**
    Implement dynamic on-device recalibration during application idle time to generate environment-specific policies.

## Patent/Research
37. **What is novel about WASWIT?**
    The combination of rigorous empirical statistical validation to derive an adaptive runtime-routing policy packaged in a zero-configuration developer toolkit.
38. **What could potentially be patented?**
    The specific architecture of separating empirical calibration from deployment, creating an ultra-low-overhead deterministic router for WebAssembly.
39. **What is the difference between your research contribution and engineering contribution?**
    The research validates the statistical bounds of crossover points; the engineering contribution operationalizes those points into an accessible SDK package.
40. **How would the system generalize to additional workloads?**
    New workloads would be introduced to the calibration suite, resulting in new policy thresholds appended to the frozen policy document.
